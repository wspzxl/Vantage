# Devlog

Running log of what got built/decided each session, and why. Kept short — this doubles as the "here's my build log" artifact for outreach.

## 2026-11-05

- Scoped the MVP: a cross-border (US–China) catalyst + anomaly tracker, multi-user, event-driven alerts over ML forecasting/backtesting. Full reasoning in the plan doc.
- Scaffolded the app: Next.js 16 (App Router, TypeScript) + Supabase (Postgres/Auth) + Resend, targeting Vercel.
- Next.js 16 landed mid-build with real breaking changes from what most docs assume: Cache Components is on by default (every runtime/cookie/DB read needs a `use cache` or `<Suspense>` boundary or the build fails), and `middleware.ts` is renamed to `proxy.ts`. Turned Cache Components off — nearly every page here is per-user/dynamic anyway (auth, personal watchlist, live-ish data), so the static-shell model would've added Suspense ceremony everywhere for no real win. Using plain `dynamic = 'force-dynamic'` on pages that need it instead, and will write `proxy.ts` (not `middleware.ts`) for the Supabase session-refresh logic.
- Installed `@supabase/supabase-js`, `@supabase/ssr`, `resend`.
- Built the Phase 1 skeleton: `lib/supabase/{client,server,middleware}.ts`, `proxy.ts` (session refresh + route protection, redirects unauthenticated users to `/login`), `app/login` (sign in/up forms + server actions), `app/dashboard` (protected layout + placeholder page), and a real landing page replacing the create-next-app starter.
- Hit a genuine toolchain bug while verifying the build: Turbopack's Tailwind v4 integration (`@tailwindcss/turbopack`/`@tailwindcss/node`) does a CJS `require()` on `magic-string`, which is ESM-only — this needs Node's `require(esm)` interop (stable on Node ≥22.12/20.19/24), but the system `node` on this machine resolves to an old Anaconda-bundled v22.6.0. Worked around it two ways: (1) downloaded a standalone Node 24 LTS into `.local-node/` inside the repo (gitignored) so the project doesn't touch the system/Anaconda Node at all, and (2) switched both `dev` and `build` scripts to `--webpack` instead of the Turbopack default, since Turbopack's own embedded JS evaluator hit the same bug independent of which Node ran it — added `postcss.config.mjs` + `@tailwindcss/postcss` for that path. `.claude/launch.json` now launches `dev` via bash with `.local-node/bin` prepended to PATH so the preview tooling picks up the right Node too.
- `npm run build` and `npm run lint` both pass clean. Verified in the browser: the only remaining error is the expected one (`proxy.ts` needs real `NEXT_PUBLIC_SUPABASE_URL`/`ANON_KEY` — not set yet since the Supabase project doesn't exist). Blocked on account creation to go further — see README's "Accounts needed."

## 2026-11-09

- Re-prioritized: demo/interaction first, real infra (Supabase/Resend accounts) later. Added `isSupabaseConfigured` as a demo-mode gate — auth is bypassed with a mock user until real credentials exist, so the UI is clickable with zero account setup.
- Corrected a scope misunderstanding from earlier: the product isn't just the single cross-border catalyst calendar. It's two parallel tracking modes, both delivered as a daily briefing:
  - **正常追踪 (normal tracking)** — a market overview the user picks from a config panel (not locked to one market — learned from prior work that paying users are financial investors broadly, so market choice needs to be flexible).
  - **蹲未来 (stake out the future)** — user-defined watch targets (a price level breaking on a stock, or "alert me on this company's next move"), evaluated against live-ish data and surfaced once triggered. Not a fixed calendar — the user sets their own target and the system watches for it.
- Built the mock-data interaction demo for both modes, no backend required:
  - `lib/data/{market-options,mock-prices,mock-news}.ts` — demo overview blurbs per market, mock prices, mock news for trigger evaluation.
  - `lib/tracking/{types,evaluate}.ts` — `WatchTarget` model + pure `evaluateTarget`/`evaluateTargets`, shared logic so the same evaluation can back an email digest later.
  - `components/tracking/TrackingProvider.tsx` — client context holding selected markets + watch targets (demo-local state; becomes Supabase-backed persistence later).
  - Three dashboard tabs: `/dashboard` (今日简报 — today's briefing: market overview cards, triggered 蹲未来 targets, 7-day catalyst preview), `/dashboard/calendar` (the original interactive catalyst calendar, kept as-is), `/dashboard/tracking` (自动化追踪面板 — market picker + watch-target manager with an add/remove form).
  - Delivery channel for now: in-app display is the "push" (shows on login); email (Resend) stays an optional channel to layer in once accounts exist, not built as a non-functional toggle.
- Two Next.js 16 lint fixes worth remembering: `react-hooks/purity` forbids calling `Date.now()` during render anywhere (client or server component) — fixed by computing it once in the page's Server Component and passing it down as a plain prop; since `cacheComponents` is already off for this app (see 11-05 entry), the one remaining server-side case is an intentional `eslint-disable-next-line react-hooks/purity`, not a `connection()`+`Suspense` dance that would only matter if we re-enabled Cache Components.
- Found and fixed a real toolchain bug: the running dev server's Tailwind v4 content scan didn't pick up classes from files created after the server started (confirmed via fetching the built CSS directly — `gap-3`/`gap-4` from original files were present, `gap-2`/`gap-1.5` from new files were silently missing, while unrelated utilities like `border`/`padding` worked fine since those classes existed before the server started). Fix: stop the dev server, delete `.next`, restart — forces a full rescan. Worth remembering if new components ever look unstyled mid-session.
- Landing page's "Sign in/Sign up" buttons still pointed at `/login`, and submitting that form called Supabase unconditionally — crashed with a raw runtime error since no project exists yet. Fixed properly rather than just redirecting around it: landing page now links straight to `/dashboard`, and all three login server actions (`signIn`/`signUp`/`signOut`) check `isSupabaseConfigured` first and no-op redirect if not. The login UI itself is untouched and will work once real credentials exist — just disconnected from the nav flow for now so nothing can hit it by accident.
- Two real product gaps flagged: (1) every screen had only been shown in its "returning user with stuff already set up" state — a brand-new user has zero selected markets, zero watch targets, zero followed tickers, and that empty state hadn't been designed at all; (2) the calendar tab was just "my personal calendar," with no discovery mechanism for a user who doesn't know what to track yet.
- Restructured the calendar tab into **话题广场 (Topic Plaza)** at `/dashboard/plaza`, replacing `/dashboard/calendar` and the old `CatalystDashboard` component (removed, superseded):
  - **热门追踪** — trending topics (`lib/data/trending.ts`, mock follower counts) with one-click follow/unfollow.
  - **猜你想追** — same-sector content-based recommendations off what the user already follows (`lib/tracking/recommend.ts`, pure function, explainable: "同属 EV/Auto，你在追 NIO").
  - **Timeline** — the old calendar view, now embedded here and driven by `followedTickers` instead of its own local watchlist state.
  - Added `followedTickers`/`followTicker`/`unfollowTicker` to `TrackingProvider` — a separate, lighter-weight concept from `watchTargets` (following a topic for its timeline+recs vs. setting a specific price/news alert on it).
- Designed real empty states instead of just handling "zero items" with a blank message: 正常追踪 with nothing selected shows inline one-click market chips right in the empty state (no forced trip to settings); 蹲未来 distinguishes "no targets set at all" (points to Plaza or Settings) from "targets set, none triggered yet"; Plaza's Timeline/recommendations each have their own empty copy pointing back at 热门追踪, which always has content since it's not personalized.
- Added a `resetAll()` escape hatch + a "查看新用户空状态" link in 追踪设置, so empty states can be previewed live instead of taken on faith.

## 2026-11-10

- Added a Chinese/English toggle for the whole app — this is meant to be shown to English-speaking founders in cold outreach, so the English mode needed to be a first-class, fully-translated experience, not just a courtesy.
- Lightweight client-side approach, not routing-based i18n (no `/en`/`/zh` paths, no `next-intl`): a `LocaleProvider` React context (`components/i18n/LocaleProvider.tsx`) holding `locale`/`toggleLocale`/`t`, persisted to `localStorage` and synced on mount via `useEffect` (default render is always `"zh"` so SSR/hydration never mismatches; the stored preference applies right after mount — same `react-hooks/set-state-in-effect` tradeoff as the `Date.now()` case from 11-09, same fix: a justified, scoped `eslint-disable`). A small `LocaleToggle` button component is dropped into the landing page and the dashboard header.
- Static UI copy (nav labels, section headers, empty-state text, form labels, etc.) lives in one dictionary, `lib/i18n/translations.ts` — `{ zh, en }` pairs keyed by string, picked via `t(key)`.
- Mock financial content (event titles, news headlines, anomaly summaries, prices) turned out to already be English-only in this codebase and was left as-is — real financial data/headlines legitimately show in their original language regardless of UI locale, so there was nothing to translate there. What did need bilingual content: `market-options.ts` (market summaries/labels), `trending.ts` (trend notes), and the 猜你想追/蹲未来-trigger copy that was being built as a hardcoded Chinese sentence inside pure functions (`lib/tracking/recommend.ts`, `lib/tracking/evaluate.ts`) — refactored those to return structured data (or take a `locale` param) instead of a pre-formatted string, so the UI decides the language rather than the data layer baking it in.
- `siteConfig.name`/`tagline`/`description` became `{ zh, en }` too; the brand name now shows "蹲未来" in Chinese and "DunWeilai" in English (the `shortName` field added back on 11-05 for exactly this).
- `app/dashboard/layout.tsx`'s header got pulled out into a client component (`DashboardHeader.tsx`) since it needed `useLocale()` and the layout itself has to stay a server component for the Supabase session check.
- Lint and build both pass clean. Verified live in the browser: toggled EN/中文 on all three dashboard tabs plus the landing page, confirmed the choice persists across a full page reload (localStorage), and confirmed no leftover Chinese text in English mode (including inside the "猜你想追" reasons, trending notes, and 蹲未来 triggered-target sentences, which are the three places that were being generated as raw strings rather than picked from a dictionary).
